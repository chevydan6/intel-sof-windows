# N100 ACX application playback test, 2026-10-13

The Lenovo 14e Chromebook Gen 3 / Google PUJJOTEEN speaker route previously produced an audible hardware tone with the SOF IPC3 firmware and HDA DMA path; see `n100-speaker-tone-test.md`. This test asked whether an ordinary Windows audio app could use the development ACX speaker endpoint.

On branch `feature/acx-speaker`, CI WDK build `38408673620` produced a signed combined probe and ACX driver. It temporarily bound to the Intel N100 audio controller (`PCI\VEN_8086&DEV_54C8`), started, and Windows showed an OK `AudioEndpoint` named `Speakers (N100 SOF speaker (development))`. The firmware session booted, IPC3 pipeline and PCM parameter replies were zero, and `test-speaker-tone.ps1 -LeavePrepared` left the path ready. `test-acx-playback.ps1` generated a 48 kHz stereo WAV and called `System.Media.SoundPlayer.PlaySync`. The call returned, but the driver reported zero streams, runs, packets submitted, packets completed, and hardware position. The script now treats any of those zero counters as a failure, rather than calling that test a pass. It cleaned up the PCM params and firmware session, with `RestoredAdspcs=0x00000F0F` and `CleanupFlags=0`.

CI WDK build `38409660762` added stream creation attempt and failure-stage counters. With that driver, `waveOutOpen` for both the default device and device 0 returned `MMSYSERR_ERROR` (1). The driver recorded `CreateAttempts=0`, so neither call reached its `EvtAcxCircuitCreateStream` callback. A direct Core Audio probe using `IMMDeviceEnumerator` found one active render endpoint and returned `S_OK` for the default endpoint and `IMMDevice::Activate(IID_IAudioClient)`. Both `IAudioClient::GetMixFormat` and `IAudioClient::Initialize` then returned `0x80070005` (`E_ACCESSDENIED`), again with zero create attempts. These commands ran through Windows OpenSSH in session 0; no `explorer.exe` process or signed-in console user was present. The evidence establishes that the current failure occurs before our stream callback, but does not prove whether a signed-in console session would succeed or whether an endpoint configuration problem also exists.

Use `tools/check-coreaudio.ps1` to repeat the API diagnosis. To resume the actual speaker test, first sign in to the Windows desktop and run the one-shot ACX package and playback test in that interactive user session. Check stream counters and audible output before claiming working application playback. The ACX driver remains development-only and is not installed persistently.

After the test, the temporary driver package, test certificate, and test-signing boot setting were removed. A normal reboot was verified at 2026-10-13 23:05:15 local time: no SOF driver provider, service, package, test trust, or test-signing setting remained, and the controller showed its normal driverless/Stopped state.
