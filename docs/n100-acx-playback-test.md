# N100 ACX application playback investigation, 2026-10-14

The Lenovo 14e Chromebook Gen 3 / Google PUJJOTEEN speaker route previously produced an audible hardware tone with the SOF IPC3 firmware and HDA DMA path; see `n100-speaker-tone-test.md`. This test asked whether an ordinary Windows audio app could use the development ACX speaker endpoint.

On branch `feature/acx-speaker`, CI WDK build `38408673620` produced a signed combined probe and ACX driver. It temporarily bound to the Intel N100 audio controller (`PCI\VEN_8086&DEV_54C8`), started, and Windows showed an OK `AudioEndpoint` named `Speakers (N100 SOF speaker (development))`. The firmware session booted, IPC3 pipeline and PCM parameter replies were zero, and `test-speaker-tone.ps1 -LeavePrepared` left the path ready. `test-acx-playback.ps1` generated a 48 kHz stereo WAV and called `System.Media.SoundPlayer.PlaySync`. The call returned, but the driver reported zero streams, runs, packets submitted, packets completed, and hardware position. The script now treats any of those zero counters as a failure, rather than calling that test a pass. It cleaned up the PCM params and firmware session, with `RestoredAdspcs=0x00000F0F` and `CleanupFlags=0`.

CI WDK build `38409660762` added stream creation attempt and failure-stage counters. With that driver, `waveOutOpen` for both the default device and device 0 returned `MMSYSERR_ERROR` (1). The driver recorded `CreateAttempts=0`, so neither call reached its `EvtAcxCircuitCreateStream` callback. A direct Core Audio probe using `IMMDeviceEnumerator` found one active render endpoint and returned `S_OK` for the default endpoint and `IMMDevice::Activate(IID_IAudioClient)`. `IAudioClient::GetMixFormat` and `IAudioClient::Initialize` returned `0x80070005` (`E_ACCESSDENIED`), again with zero create attempts. The same result occurred in the signed-in desktop session 1, so SSH session isolation was not the cause. `GetDevicePeriod` and `IsFormatSupported` with explicit 48 kHz stereo S32 also returned `E_ACCESSDENIED`.

Build `38421003199` aligned the ACX circuit name with the INF interface reference string `Speaker0`. Windows then copied the 48-byte `PKEY_AudioEngine_OEMFormat` from the INF to the endpoint, but the active `PKEY_AudioEngine_DeviceFormat` was absent. A temporary write to that endpoint property failed with `Requested registry access is not allowed`; no value was written. [Microsoft documents endpoint properties as set by the audio service and read-only to clients](https://learn.microsoft.com/en-us/windows/win32/coreaudio/audio-endpoint-properties).

The live controller's `DEVPKEY_Device_SecuritySDS` was `D:P(A;;GA;;;SY)(A;;GA;;;BA)`, inherited from the earlier `sofprobe.inx` package. Windows Audio (`Audiosrv`) runs as `NT AUTHORITY\LocalService`; it has no access under that descriptor. This is a strong candidate for `E_ACCESSDENIED`. Commit `069ad73` adds Local Service read/write/execute access in `sofplay.inx` and extends the Core Audio probe. WDK CI build `38422050078` passed. The candidate is **not yet validated**: replacing the package left Windows PnP paused during device restart (`setupapi.dev.log` stopped at `{Restarting Devices}`), and rebooting left the package staged but not bound. A second install paused at the same step.

To separate stale device-instance security from the new INF, the driverless controller was removed and rescanned with `pnputil`. This cleared `DEVPKEY_Device_SecuritySDS` and survived reboot. Installing build `38422050078` on the clean instance then rebooted Windows unexpectedly. The earlier known-starting build `38421003199`, installed in a separate test boot on the same clean instance, did the same. Neither build bound a driver or created an endpoint. The access-rule hypothesis still needs a successful binding before it can be tested. Do not treat either build as a working audio driver.

The apparent PnP stall was a kernel crash. Windows recorded four `0x19 BAD_POOL_HEADER` bugchecks with parameter 1 `0x22`, which [Microsoft describes as a free of an address without a pool tracking entry](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-0x19--bad-pool-header). Microsoft CDB analyzed the 2026-10-14 00:42 dump: `nt!ExFreePoolWithTag` was called from `sofplay+0x2596`, within `SofPlayEvtFreePackets`, during `Acx01000!Acx::AfxRtStream::FreeStreamAllocations` / `Deinitialize`. The stream cleanup callback also freed the same packet allocations without clearing `context->Packets`, so the later ACX packet-free callback could free them again. The precise earlier free is inferred from source and stack ordering; the dump directly proves the invalid free in the packet callback. A source fix now gives the allocations one atomic owner, clears the context before freeing, and avoids publishing partially allocated packets. It needs a WDK build and controlled hardware retest before claiming the crash is fixed.

Commit `e14db49` fixed packet ownership. WDK CI build `38426093162` installed and started without the prior pool crash. The controller was `OK`, the speaker endpoint was active, and the live security descriptor included Local Service read/write/execute access. Core Audio then returned `0x80070032` (`ERROR_NOT_SUPPORTED`) for `GetMixFormat`, `GetDevicePeriod`, `IsFormatSupported` with explicit stereo S32, and `Initialize`; no create-stream callback was reached. This establishes that the earlier access denial was resolved, while playback is still blocked before stream creation.

Commit `e03edfe` assigned the advertised format as the explicit default. WDK CI build `38426855276` also installed and started, but Core Audio returned the same `0x80070032`. A read-only `IOCTL_KS_PROPERTY` probe in `tools/probe-ks-pins.ps1` found two pins. Pin 0 is an input/sink host pin and advertises a single 48 kHz, stereo, 32-bit PCM range. `KSPROPERTY_PIN_PROPOSEDATAFORMAT` returns the corresponding 104-byte `KSDATAFORMAT_WAVEFORMATEXTENSIBLE`. Pin 1 is an output/noncommunicating speaker bridge pin. `KSPROPERTY_PIN_DATAINTERSECTION` on pin 0 returned Win32 50 (`ERROR_NOT_SUPPORTED`) even for the driver's advertised range; this may be relevant, but it is not yet proven to be the Core Audio failure source. The endpoint still has no `PKEY_AudioEngine_DeviceFormat` value despite the OEM format being present.

The `38426855276` package was removed after this test. Windows was rebooted and verified with no `sofplay.inf` package, no test-signing boot setting, and neither ACX9 nor ACX10 signer certificate in TrustedPublisher or Root. The temporary Windows SDK debugger installation used for crash analysis was uninstalled. The 635 MB Windows `MEMORY.DMP` was copied to the ignored local `build/acx-38422050078/MEMORY.DMP`, its SHA-256 was verified on both machines, and the Windows copy was removed. Windows C: free space rose from 2.76 GB to 3.87 GB. The controller reports `OK` with no SOF provider; the desktop session was absent at the final check, so the corrected driver has **not** been tested from an interactive desktop. Check `tools/check-coreaudio.ps1` in a signed-in desktop session during the next controlled install. Do not claim application playback until stream counters and audible output both confirm it.

After the final crash and before the two corrected-build tests, the temporary driver package, both test certificates, the interactive scheduled task, and test-signing boot setting were removed. The 2026-10-14 00:43 local boot verified no SOF driver provider, service, package, test trust, test-signing setting, or probe registers. The controller was driverless but reported `Error / CM_PROB_FAILED_INSTALL` after the device-instance reset, where it had previously shown `Stopped`; therefore the previous `verify-acx7-rollback.ps1` assertion failed. This status difference remains to be investigated before calling the machine fully restored to its prior device state.

Commit `b23b2a0`, WDK CI build `38430922628`, added the same 48 kHz stereo S32 format to the DEFAULT processing-mode list. The live KS probe showed the format in both RAW and DEFAULT mode, and the driver again started with an active speaker endpoint and Local Service ACL. `GetMixFormat`, `GetDevicePeriod`, `IsFormatSupported`, and `Initialize` still returned `0x80070032`. A scheduled task ran the Core Audio check in the signed-in Windows desktop session 1 and found the same result, ruling out SSH session isolation for this build. `tools/check-endpoint-properties.ps1` read the actual endpoint `IPropertyStore`: OEMFormat was a valid 40-byte stereo S32 `WAVEFORMATEXTENSIBLE`, while DeviceFormat was `VT_EMPTY`.

Commit `126e09d`, WDK CI build `38432445499`, changed only the advertised format to 24 valid bits in 32-bit slots, with matching OEMFormat. The package installed cleanly after the previous one was removed and Windows rebooted. RAW and DEFAULT KS lists both show the new format. The active endpoint's OEMFormat changed to the correct 40-byte value, but DeviceFormat remained `VT_EMPTY`, and all four Core Audio calls still returned `0x80070032` in SSH session 0. For a controlled diagnostic, the endpoint's DeviceFormat was set to the OEMFormat via `IPropertyStore`, the Core Audio calls were repeated without improvement, and DeviceFormat was restored to `VT_EMPTY`. A one-range `KSPROPERTY_PIN_DATAINTERSECTION` probe also returned Win32 50, matching the two-range probe. Neither a missing DeviceFormat property by itself nor the S32-versus-24-in-32 choice explains the failure.

State during build `38432445499` testing: the development ACX driver was bound as `oem23.inf`, the controller reported `OK`, the endpoint was active, test signing was enabled, and the ACX12 test certificate was trusted. There was no signed-in Windows desktop session after that reboot. `SofPlayCoreAudioCheck` was registered for the next sign-in but removed before it ran. Audible playback has **not** been demonstrated.

A separate diagnostic branch, `experiment/acx-16bit-format` at `26d1ed9`, used 48 kHz stereo 16-bit PCM as the advertised format. Its stream callback intentionally still rejects four-byte frames, so this build could only test pre-stream negotiation. WDK CI build `38433604729` passed and installed cleanly on the N100. `IAudioClient::GetMixFormat`, `GetDevicePeriod`, `IsFormatSupported` (the probe's explicit S32 request), and `Initialize` still returned `0x80070032`; the active endpoint had a new ID. The 16-bit build was removed after the test. A final reboot verified controller `OK`, no SOF driver bound or staged, test signing disabled, no ACX9–ACX13 test certificates trusted, and no scheduled diagnostic task. The earlier ACX12 desktop-session check was not run because Windows had no signed-in desktop after its reboot; ACX11 already reproduced the error in desktop session 1. The unchanged failure with S32, 24-in-32, and S16 formats points away from sample width and toward a more basic endpoint or pin contract issue, but the exact source of Win32 50 remains unproven.

After rollback, Windows build `26300.9550` reported Core edition (not N). `AudioEndpointBuilder`, `Audiosrv`, and `MMCSS` were running and set to automatic. `audiodg.exe`, `AudioSes.dll`, `MMDevApi.dll`, `AudioEng.dll`, and `ksuser.dll` were present. This does not prove that every audio component is healthy, but it rules out missing core service binaries or stopped audio services as the immediate explanation. Microsoft's ACX `AudioCodec` render sample uses the same sink/source pin types, speaker bridge category, and `KSNODETYPE_ANY` endpoint association as this driver; its stock `EvtAcxPinSetDataFormat` returns `STATUS_NOT_SUPPORTED`. The cause of the pre-stream `0x80070032` still requires further tracing rather than a speculative callback change.

Further analysis of the saved 00:42 crash dump with `!wdfkd.wdflogdump Acx01000 -d` decoded the ACX framework recorder. It shows a successful `CreateStream`, followed by `EvtAcxStreamPrepareHardware` returning `0xc00000a3` (`STATUS_DEVICE_NOT_READY`) on the transition from Stop to Pause. This qualifies the earlier "before stream creation" conclusion: subsequent application probes did not create streams, but initial endpoint setup did in the saved crash. `SofPlayEvtStreamPrepare` requires the user-space SOF firmware/pipeline test to have already prepared the hardware ring. Whether this initialization ordering also explains the newer `ERROR_NOT_SUPPORTED` needs a fresh hardware test.

Commit `463051a` fixes a separate packet allocation contract error: with two page-rounded MDL allocations, the first audio packet must end at the first allocation's page boundary and the second must start at offset zero. Previously both offsets were zero, leaving a gap between the audio packets when mapped together. The allocation callback now supports the documented one or two packets, and sets the first packet offset to `allocationBytes - PacketSize`, matching [Microsoft's allocation callback example](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/acxstreams/nc-acxstreams-evt_acx_stream_allocate_rtpackets). WDK CI build `38440825943` passed. Hardware validation is pending.

Build `38440825943` installed cleanly as `oem23.inf` with the controller `OK` and Local Service access. With `Audiosrv` and `AudioEndpointBuilder` stopped, the driver initially reported zero stream attempts. The test then staged the validated IPC3 image, booted SOF, and prepared the speaker pipeline before restarting the audio services. Windows created two streams without a recorded callback failure. `GetMixFormat`, `GetDevicePeriod`, and `Initialize` all returned `S_OK`; the periods were 100,000 / 30,000 in 100 ns units, and Initialize allocated 4,800 frames. Both OEMFormat and DeviceFormat now held the correct 40-byte 24-in-32 stereo format. The combined changes clear the prior failure; this experiment does not isolate which change caused the former Win32 50.

A subsequent WAV playback test needed a fresh device because the probe intentionally permits only one ROM-entry attempt per device instance. `pnputil /restart-device` reset that guard without a full Windows reboot. With the services stopped during firmware staging and pipeline preparation, a three-second 48 kHz stereo WAV played through `System.Media.SoundPlayer`. The live counters were `StreamsCreated=1`, `CreateAttempts=1`, `RunCalls=1`, `PacketsSubmitted=301`, `PacketsCompleted=301`, `HardwarePosition=31488`, `HardwareStatus=0x20`, and no recorded failure. This verifies Windows application-to-driver packet flow and hardware DMA progress; it does not independently establish audible speaker output. Audible confirmation was requested from the user.

Before freeing the shared ring, the test stopped Windows audio services so their streams could close. PCM parameter release and session stop succeeded, restoring `ADSPCS=0x00000F0F` with `CleanupFlags=0`; the services were then restarted. `tools/test-acx-playback.ps1` now applies this ordering, restores the original service running states, and supports a repeatable elevated invocation:

```powershell
.\test-acx-playback.ps1 -RestartDevice -FirmwarePath C:\path\to\sof-adl-n-ipc3.ri
```

This remains a development test with temporary test signing, not persistent audio support. The final driver needs to own firmware/pipeline initialization before stream preparation and handle shutdown, suspend/resume, and failures without this service-stop test harness. Automatic firmware startup has not been implemented by these fixes.

The updated repository test script was then run on the N100 with `-RestartDevice -FirmwarePath`. It passed: one stream and run, 301 submitted packets, 302 completion notifications, hardware position 35,328, status `0x20`, and no recorded callback failure. The extra completion notification reflects hardware-clock reporting after the submitted data; exact end-of-stream handling is still unfinished and should not be inferred from these counters. Both audio services were running/automatic after cleanup, the controller and speaker endpoint were `OK`, and session restoration again returned zero cleanup flags.

Final cleanup after these tests removed the development driver package and ACX14 test certificate trust, disabled test signing, and rebooted Windows. Verification found controller `OK`, no bound provider/INF, no SOF package, no ACX9–ACX14 trusted test certificates, and no diagnostic scheduled task. The temporary Windows SDK debugger was uninstalled, and only the copied analysis dump was removed from Windows; the saved local crash dump remains available. Windows C: free space was 3.84 GB before the final reboot. This leaves no persistent audio driver installed. The packet correction and successful test harness are preserved on `feature/acx-speaker` for the next implementation stage.
